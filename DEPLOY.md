# Деплой frontend (plaza-web)

Next.js 16, App Router, клиентский рендеринг с обращениями к API из
браузера. Деплоится независимо от бэкенда, но **после** него: без
работающего API фронтенд показывает пустые экраны.

Инструкция по бэкенду и БД — в `plaza-api/DEPLOY.md`.

---

## 1. Переменные окружения

| Переменная | Значение |
| --- | --- |
| `NEXT_PUBLIC_API_URL` | адрес задеплоенного API, например `https://plaza-api.onrender.com` |

Это единственная обязательная переменная. Префикс `NEXT_PUBLIC_`
означает, что значение попадает в клиентский бандл — оно **вшивается на
этапе сборки**, а не читается в рантайме. Поменяли адрес API → нужен
пересбор, а не просто перезапуск.

Адрес указывается без завершающего слэша.

## 2. Сборка

```
Build Command:  npm ci && npm run build
Start Command:  npm run start
```

Node 20+. `npm run build` выполняет проверку типов, так что ошибка
типизации валит деплой — это ожидаемо.

Платформа не важна: Vercel, Render (Web Service), любой контейнер с
`next start`. На Vercel Build/Start Command определяются автоматически,
нужно задать только `NEXT_PUBLIC_API_URL`.

## 3. Связка с бэкендом (самая частая поломка)

В `plaza-api` переменная `CORS_ORIGIN` должна содержать **точный origin
этого фронтенда**: тот же протокол, тот же хост, без слэша на конце.

```
# plaza-web
NEXT_PUBLIC_API_URL=https://plaza-api.onrender.com

# plaza-api
CORS_ORIGIN=https://plaza.example.com
```

Если origin не совпадает, браузер отклоняет каждый запрос до попадания в
роуты API. В интерфейсе это выглядит не как ошибка, а как бесконечная
загрузка и пустые списки. Проверяется в DevTools → Network: запрос со
статусом `(failed)` и сообщением про CORS.

Второй нюанс: аутентификация держит refresh-токен в cookie, запросы идут с
`credentials: "include"`, а cookie по умолчанию выставляется с
`SameSite=Lax`. Браузер вернёт её только если фронтенд и API в пределах
одного регистрируемого домена: `plaza.example.com` + `api.example.com` —
да, `plaza.vercel.app` + `plaza-api.onrender.com` — нет.

Если домены разные, симптом такой: вход проходит, а примерно через 15
минут пользователя выбрасывает на логин без объяснений. Решения два —
посадить оба сервиса на поддомены одного домена (лучше) либо выставить
`COOKIE_SAMESITE=none` в переменных окружения API, и тогда оба сервиса
обязаны работать по HTTPS. Подробнее — в `plaza-api/DEPLOY.md`.

## 4. Проверка после деплоя

1. Открыть `/login`, войти под менеджером проекта.
2. Главная: касса и последние операции заполнены (не «Загрузка…»).
3. Создать расход в «Кассе» — он появляется в списке.
4. «Аналитика» → вкладка «Объекты»: данные отображаются.
5. «Отчёты» → любой отчёт скачивается .xlsx-файлом.

Если п.1 проходит, а дальше пусто — проблема почти всегда в `CORS_ORIGIN`
на стороне API, а не во фронтенде.

## 5. E2E-проверка

`tests/e2e/demo-flow.spec.ts` — полный сценарий стройки (приход денег →
поставщик → аванс → склад и материал → закупка → блоки с этажами →
списание на этаж и на блок целиком → отчёты → отмена закупки). Гоняется
против **живого** бэкенда и **создаёт реальные данные**, поэтому на
продакшене запускать нельзя — только локально или на staging:

```bash
E2E_BASE_URL=https://staging.example.com npx playwright test
```

Требуются сид-аккаунты из `plaza-api/prisma/seed.ts`; пароли
переопределяются переменными `SEED_MANAGER_PASSWORD` и т.д.

## 6. Откат

Пересборка предыдущего коммита. Состояния на стороне фронтенда нет —
откат безопасен и не требует действий с БД. Единственное исключение: если
релиз шёл вместе с миграцией API, откатывайте бэкенд по инструкции в
`plaza-api/DEPLOY.md`, а фронтенд — следом.
